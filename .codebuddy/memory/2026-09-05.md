## 修复 anydoc 的两个 MTEF 崩溃（都是真实触发，非理论问题）

讲义31（134709 B 的 Word 版 docx，105 个 OLE）直接喂 anydoc 会挂，两处：

1. **`build_ast` 栈下溢 panic**（`mtef.rs:490`）
   `let parent = *stack.last().unwrap()`，而 `tag::END` 分支无条件 `stack.pop()`，
   多一个 END 就把 root 也弹掉 → 下一轮 `unwrap()` 崩。
   修：`stack.last().copied().unwrap_or(0)`，且 `if stack.len() > 1 { stack.pop() }`。

2. **`dimension_arrays` 死循环 → 25 GB OOM**（`mtef.rs:437`）
   `while count < size` 里，`count` **只在 nibble == 0x0f 时 +1**；同时
   `r.u8().unwrap_or(0)` 越界后一直返回 0 ⇒ `pos` 不前进、`count` 不增加、
   `_array` 每次迭代 push 2 个 String。实测 abort：
   `memory allocation of 25769803776 bytes failed`（= 2^30 × 24 B，正好是
   `Vec<String>` 元素大小，反推 ~2^30 次迭代）。
   修：函数改返回 `Option<()>`，`r.u8()?` 越界即 None，调用处两处加 `?`。

修复后不再崩，但对**这份讲义的 Equation.3 质量仍差**：87/105 完全解码失败退回占位符，
剩下的多是 `$Ȁ$` 乱码或空结构（`\begin{array}{l}\end{array}`）。
**结论：Equation.3 仍要依赖 LibreOffice，anydoc 自带 MTEF 目前打不过它。**
（字符查表本身没问题：`char/0x0041` 格式与 `MTEF_CHARS` 的 key 一致。）

## mathtype2omml 实测：104/105 是虚报，只对 MathType 有效

装好跑讲义31，报 `104/105 succeeded`，但解包验真：
`m:oMathPara` = 104 里面**绝大多数是空壳** `<m:oMathPara><m:oMath/></m:oMathPara>`。
即 Equation.3（MTEF v3）被换成空壳、公式凭空消失；只有
**MathType（Equation.DSMT4）真填进了内容**——正好是 LibreOffice 做不了的那 10 个。
1 个失败是 oleObject88（质量校验拦下：`Empty OMML critical slot: m:den`）。

## 最终方案：两条路线互补 + 合并（讲义31 已 0 缺口交付）

| 路线 | Equation.3 (95) | MathType (10) |
|---|---|---|
| LO docx→odt→anydoc | ✅ 质量好 | ❌ 静默丢 |
| mathtype2omml→anydoc | ❌ 变空壳 | ✅ 质量好 |
| anydoc 自带 MTEF | ❌ 87 失败 + 乱码 | — |

新脚本 **`scripts/merge-equation-routes.ps1 -Base <odt版md> -Supplement <omml版md>`**：
按文档顺序把 Base 的 `<!-- embedded object: ... -->` 逐个替换成 Supplement 的数学块
（先 `$$..$$` 再 `$..$`）。**数量不匹配就报错退出**，因为 off-by-one 会把公式安到别的题上。
两份输入同源同段落结构（实测第13题都从第 119 行开始），顺序对齐可靠。

讲义31 交付结果：6960 B、**210 个 `$` 定界符、4 张题图引用全部可达、0 未转换**
（起点是 4.6 KB 且公式全空的 `01直接解析的结果/` 版本）。

## wmf-to-png.ps1 加了 MinWidth/MaxScale

## 诊断：anydoc 自带 MTEF 在讲义31 的失败分布（回答"能否在 anydoc 改代码实现"）

忠实复刻 `mtef.rs::decode_stream` 的记录循环（`D:\tools\work\replay_mtef.py`）跑 105 个流：
**37 OK / 68 fail**。失败集中在三类记录解析错误：

- `eof in tag 1`(LINE) 越界 ≈ 28 个（LINE 的 RULER 子记录 / opts 布局理解偏）
- `eof in tag 18`(EQN_PREFS) 越界 ≈ 17 个（`dimension_arrays` 仍脆弱：count 只在 nibble=0x0f 时 +1，v3 布局下几乎不递增 → 越界）
- `unhandled tag 49/50` ≈ 11 个（走 `match` 的 `_ => return None`，整条公式作废）

**根因 = MTEF version**：各流 `body[0] = 0x03` → 这是 **MTEF v3**（Equation.3）。
anydoc 的 `mtef.rs` 是基于 **MathType v5** 逆向的，对 v3 的记录布局理解不全
（LibreOffice 有完整 v3+v5 实现，所以 ODT 路线 0 缺口）。

**结论**：能在 anydoc 改代码实现，但本质是"补 MTEF v3 支持"——
要么逐个修 LINE/EQN_PREFS/未知 tag 的 v3 布局（需对照 v3 规范或 LibreOffice 源码），
要么把 `_ => return None` 改成容错跳过（简单跳过会级联错位，不够）。
工程量大、且重复造 LibreOffice 已成熟的轮子。当前**双路线合并已 105/105 且零核心改动风险**，
是更稳的交付选择；补 v3 适合作为长期"去 LibreOffice 依赖"目标。

## 已动手补 mtef.rs 的 v3 支持（本会话）

**根因（最终定位）**：Equation.3 = MTEF v3，其记录 tag 字节是 **nibble-packed**：
低 4 位 = 记录类型，高 4 位 = options/flags，**没有单独的 opts 字节**。anydoc 之前按 v5 规范
（整个字节=type + 后续 opts 字节）解析，把 `0x12` 误判成 `EQN_PREFS(18)` 而非 `CHAR(2,flags=1)`，
导致整条流字节错位 → 68/105 失败。LibreOffice 的 `mathtype.cxx` 正是 `nRecord = nTag & 0x0F`。

**已改 `mtef.rs::decode_stream`**：读 MTEF version 字节，`is_v3 = version <= 3`。
- v3：`let byte=r.u8(); (byte&0x0F, byte>>4)` 当 (t, opts)，记录内部布局同 v5（仅 opts 来源不同）。
- v5：保持原逻辑（t + 单独 opts 字节）。
- CHAR 分支按 is_v3 区分：v3 先读 16-bit mtcode 再 typeface（无 CHAR_ENC 字节）；v5 原样。
- COLOR/COLOR_DEF 分支 v3 不读单独 options 字节。
**`cargo check --lib` 编译通过（0 error，仅 pre-existing unused-const 警告）。**

**验证**：`D:\tools\work\replay_v3.py`（v3-aware 复刻）跑 lecture31 的 105 个流，
**不越界 37 → 93 / 105**。剩余 12 个失败：大 pos 的 LINE/CHAR 边界、个别未知 tag 50（次要）。
首个 OK 流的 CHAR mtcode 是标准 MathType 编码（0x7883 等），说明解析节点序列合理。

**第二个未解问题（字符映射）**：v3 的 CHAR `mtcode` 是 **font-relative**（`font<<8|char`），
而 `char_latex` 假设 `mtcode` = **Unicode 码点**（`MTEF_CHARS` 表键是 Unicode，如 `char/0x03b1`）。
`char::from_u32(0x7883)` 会得到汉字而非 α/∑。要正确需 **MathType font-relative→Unicode 映射表**，
但 `mtef_ref/chars.py` 只有 Unicode 键（无 font-relative 数据）。
**mathtype2omml 能正确转 MathType(v5) 字符，应含 font-relative 映射，可从它提取补全。**
→ 下一步：提取 MathType 字体字符映射，对 v3 用 font-relative 键查/生成表；或双路线兜底。

## PowerShell 踩坑（本会话新增）

- 中文路径在命令里仍会被按 GBK 解码成乱码（`Test-Path` 假阴性）。可靠办法：
  **只用 ASCII 条件**做筛选，例如
  `Get-ChildItem -LiteralPath 'D:\Books' -Recurse -Filter '*31*.md' | Where-Object { $_.FullName -notmatch 'out_docx|01' }`，
  中文只出现在 `-Filter`/路径里而不出现在手写字符串中。
- `Remove-Item` 管道绑定在本环境会被 Safe-Delete 拦下报
  `InputObjectNotBound`；改成 `foreach ($f in $list) { Remove-Item -LiteralPath $f.FullName }`。
- `Remove-Item -LiteralPath` **不支持通配符**（要删 `*.png` 得用 `-Path`）。
- $1 **.NET 正则替换里的 `$` 必须写 `$$`**：`.Replace($t, '$1')` 会把 `$` 定界符一起吃掉
  （实测把 `$$y=kx+b$$` 变成裸 `y=kx+b`）。正确写法 `'$' + '$${1}$$'` 即 `$$${1}$$`，
  其中 `$$`=字面 `$`、`${1}`=捕获组 1。
- `$env:RUST_BACKTRACE=full` 这种赋值若被引擎误解析成命令，改用单独一行再跑。
