## 调研：doc/docx → Markdown 的转换路径

结论（已答复用户）：

- 六种入口（Rust API / CLI / Node / Python / WASM / Agent Skill）都是同一 Rust 内核的薄封装，
  doc/docx 输出逐字节相同。差异只在并发与部署：Node 用 napi `AsyncTask`（libuv 线程池，
  不阻塞事件循环）；Python 用 `py.detach` 释放 GIL；WASM 无文件系统（无 `to_markdown(path)`）；
  CLI 每文件一次进程启动，批量偏慢。
- 云端 OCR（Firecrawl Parse）只对 PDF 的 `needsOcr` 触发（`node/anydoc.js` 的 `sendsToHosted`
  判断 `error.code === 'needsOcr'`），对 doc/docx 无效。
- 内核里 doc / docx 是两套不同解析器：
  - `.doc`（`src/formats/doc/`）：OLE2/CFB → FIB → Clx/PlcPcd piece table（CP 按 UTF-16 计，
    压缩片按 `FibBase.lid` 选 ANSI 代码页）→ CHPX/PAPX FKP → STSH 样式链 → PlfLst/PlfLfo；
    段落/表格靠属性**推断**（`sprmPFInTable` + `Tap` + `shared::grid::build_edge_table`）。
    **不支持公式**。
  - `.docx`（`src/formats/docx/`）：ZIP/OPC → `_rels/.rels` 定位主 part → `w:document/w:body`
    XML 树直接映射块；styles/numbering/footnotes 由 rels 定位（有约定路径兜底）；
    Strict 命名空间在 `src/package/xml.rs` 归一化到 Transitional。支持 OMML → LaTeX。
  - 两者都产出 `model::Document { blocks, notes, assets }`，共用 `src/shared/` 与唯一的
    GFM 序列化器 `src/render/markdown/`。PDF 是唯一绕过模型直出的（pdf-inspector）。
- 保真度：docx > doc。建议 .doc 先另存 .docx 再转。
- 特殊路由：内容以 `{\rtf` 开头但扩展名/格式为 `Doc` 的文件走 RTF 解析器（`src/formats/mod.rs`）。
- 基准（README）：docx 88、doc 87，均高于 markitdown/docling/mammoth/pandoc/libreoffice；
  语料不入库，评测脚本在 `bench/`。

## 实测：.doc 里的公式在 anydoc 输出中会消失

用户给的教师版讲义 31（`讲义31：全国初中数学竞赛模拟卷（一）.doc`），`doc_to_md` 转换成功（16ms, 4713B），
但所有公式缺失。已在源码确认原因：

- `src/formats/doc/mod.rs:944` 的 `picture_at` 把内联图（含 WMF 公式）加进 `Document.assets`
  （本份抽出 105 个 WMF）。
- `src/render/markdown/inline.rs:198` 的 `render_image` 对 `ImageSource::Asset | Unavailable`
  **只输出 alt 文本**；本份图片 alt 全为空字符串 → 公式在 md 中零字节。
- `examples/convert.rs --assets <dir>` 是个有用的旁路：把 WMF 批量导出到磁盘，
  再用 PowerShell `[System.Drawing.Imaging.Metafile]` 渲染成 PNG（已实测可用，
  `Bitmap::new($w, $h)` 不是 `New-Object`，第一张是 "$(x^2+x+1)^3$"）。
- 根本修复路径：.doc → .docx（需 LibreOffice 的 `soffice --headless --convert-to docx`），
  再让 anydoc 走 docx 路径，OMML → LaTeX。Firecrawl Parse 的 `--ocr hosted` 只对 PDF 的
  needsOcr 触发，对 .doc 无效（`node/anydoc.js:36-38` 的 `sendsToHosted`）。
- 本机未装 LibreOffice（`C:\Program Files\LibreOffice\program\soffice.exe` 不存在）。

**更正（已实测证伪上面的"根本修复路径"）**：装了 LibreOffice 后实测，docx / odt / pdf 三条路
**都拿不回公式**——anydoc 转出来都是 ~4.7KB、公式全空：
  - `.doc → .docx`：解包后 `oMath` 出现 0 次、`word/media` 不存在、`oleObject` 0 次，
    即 LibreOffice 把公式（WMF 图）直接丢弃；anydoc 结果 4723B。
  - `.doc → .odt`：anydoc 结果 4692B，md 里 `$` 出现 0 次，无 MathML → LaTeX。
  - 结论：该批讲义的公式在原 doc 中**只是 WMF 呈现图**（Equation 3.0/MathType），
    没有公式语义，LibreOffice 也不识别。唯一能取回内容的是
    `convert --assets` 导出 WMF → 渲染 PNG → OCR/多模态识别。

**LibreOffice 环境备忘**：
  - 已把 `C:\Program Files\LibreOffice\program` 加入**用户级** PATH（已执行）。
  - `Get-Command soffice` 解析到 `soffice.com`（控制台版，会等待并回显）；
    `soffice.exe` 是 GUI stub，直接调用会立即返回且不回显输出——这是早期命令"无输出"的原因。
  - 远程/长驻 shell 改完 PATH 后需刷新：
    `$env:Path = [Environment]::GetEnvironmentVariable('Path','Machine') + ';' + [Environment]::GetEnvironmentVariable('Path','User')`
  - 无害告警 "Could not find platform independent libraries <prefix>" 可忽略。

## 公式问题的最终答案：Equation.3 OLE → OMML → LaTeX

用户用 **Word**（不是 LibreOffice）手动把 .doc 转成了 .docx（134709 B）。解包结果：
`word/embeddings/oleObject1..105.bin`（每个是 OLE2 复合文档，头 `D0 CF 11 E0`，内含
Equation Native/MTEF）+ `word/media/image1..91.wmf`（预览图），`m:oMath` **0 个**、
`<o:OLEObject ProgID="Equation.3">` **105 个**。

- anydoc 输出 "Embedded object: Equation.3" 的原因：`src/formats/docx/content.rs:586`
  取 OLE 的 ProgID，VML 预览图无 descr，于是 `format!("Embedded object: {prog_id}")`。
  anydoc **没有 MTEF 解码器**（`src/shared/math/` 只有 omml.rs / mathml.rs / tex.rs）。
- **解法（用户偏好，不用 LibreOffice）**：让 Word 自己把 Equation 3.0 转成新版公式
  （OMML）。Word 2016+ 打开旧公式会提示转换，且支持批量（微软官方支持文档
  "Editing equations created using Microsoft Equation Editor"）。转完另存 .docx
  → anydoc 直接出 LaTeX，全程无 LO。
- **验证过的退路**：LO 中间层 docx→docx 会把 Equation.3 转成 OMML（97 个 `m:oMath`
  + 2 个 `m:oMathPara`），anydoc 再转出 **132 个 LaTeX + 8 处插图**，答案部分公式也在。
  LO 产物只作中间层，最终 md 由 anydoc 重新生成，所以 LO 的排版丢失不影响结果。
  （注意：LO 的 **.doc** 导入器会丢弃这些 OLE，所以必须先由 Word 转成 .docx。）

已写 `scripts/docx-equations-to-md.ps1 -Root <dir>`：自动检测 docx 是否含 `m:oMath`，
含则跳过 LibreOffice；否则走 LO 中间层；最后 `doc_with_images` + `wmf-to-png` + 引用改写。

## 更优路线：docx → LibreOffice 转 ODT → anydoc（连 MathType 一起解决）

那份讲义**混用两种公式引擎**：`Equation.3` 95 个 + `Equation.DSMT4`（MathType）10 个，共 105。

- LibreOffice **docx→docx**：只转了 95 个 Equation.3 → OMML（97 个 `m:oMath`），
  **10 个 MathType 一个都没转**，仍以 `o:OLEObject` 留在包里 → anydoc 输出
  `![Embedded object: Equation.DSMT4](..._files/4.vndmsoleobject)`。
- LibreOffice **docx→odt**：content.xml 里 `<math:math>` 是 0，但 `draw:object` 有 105 个——
  公式被存成嵌入对象目录，anydoc 的 `src/formats/odf/text.rs:452` `formula_tex`
  会跟进对象目录的 content.xml 读 MathML。
  实测 anydoc 转 ODT：**130 个 `$` LaTeX，`Embedded object` 残留 0**，
  **MathType 公式也一起转出来了**。比 docx 中间层更彻底。

**结论：中间层用 `--convert-to odt`，不要用 `--convert-to docx`。**
`scripts/docx-equations-to-md.ps1` 已改为 ODT 路线。

## 更正：ODT 路线并未解决 MathType，只是"静默丢失"

上一节结论**部分错误**，以本节为准。

- ODT 路线测得 `Embedded object` 计数为 0，一度以为 105 个公式全转成功。
  实际是**静默丢失**：ODF 路径不像 docx 路径那样生成 `Embedded object: {ProgID}` 的
  alt 文本，所以没转换的对象在文本里不露痕迹。
- 真实对比：docx 中间层 **132 个 `$`**，ODT 中间层 **130 个 `$`**——基本相同。
  **第 13 题（一次函数）的 ~10 个对象两条路线都没转出来**，正好对上 Word docx 里的
  **10 个 `Equation.DSMT4`（MathType）**——它们集中在第 13 题。
- 结论：**LibreOffice 处理不了 MathType（Equation.DSMT4）**，Equation.3 可以。
  要转 MathType 需要 MathType 本体（Convert Equations 批量）或 GrindEQ 等商业工具，
  否则只能用预览图（WMF）兜底。
- 两条路线仍需对比后再定：docx 路线会在正文留可见的 `Equation.DSMT4` 垃圾文本，
  ODT 路线静默（看起来更干净但更容易漏检）。脚本里 `unconverted` 计数对 ODT 路线
  **不可靠**，要按 `$` 数量和人工抽查判断。

## doc_with_images 的缺陷修复：非图片资源不再输出 ![]()

`Asset::media_type` 不是 `image/*` 时（如 `application/vnd.ms-ole-object`、
`application/octet-stream`）输出 `![...](x.octetstream)` 会永远是坏图。
改为：是图片才 `![alt](url)`，否则输出普通链接 `[alt](url)`，
字节仍可达但不会渲染成坏图。加了 `Renderer::is_image`。

## WMF→PNG 渲染的 himetric 陷阱

`System.Drawing.Imaging.Metafile.Width/Height` 返回的是 **himetric（0.01mm）**，
不是像素。直接用它建画布会把矢量图放大 ~26 倍；WMF 记录里字号、坐标是
小整数（点距几到几十），放大后取整让字形叠在一起——视觉上"公式内容粘成一团"。
正确像素 = `round(himetric * dpi / 2540)`。经验值 300 dpi 出 40–170px 宽
（ID 0：1424x669 himetric → 168x79 px，公式 `(x²+x+1)³=1` 清晰；
ID 2：分数 3/4；ID 11：斜体 k），且已用肉眼看图确认无叠。

背景必须 `g.Clear(White)`——WMF 无背景，透明 PNG 在深色 Markdown 主题上不可读。

已写 `scripts/wmf-to-png.ps1 <dir> [-Dpi 300]`，处理 `<stem>_files/` 目录。
anydoc 自带的 GFM 序列化器对资源图片只输出 alt 文本，asset 落盘后由本脚本完成可视化。

## MathType → OMML 的开源方案（解决上一节遗留的 10 个 .octetstream）

工具：**`uwjiaoxing/mathtype2omml`**（MIT，Python ≥ 3.10）
仓库：https://github.com/uwjiaoxing/mathtype2omml
（fork 自 `a917470154/mathtypejx`）

- 直接解析 docx 里的 **MathType OLE（Equation.DSMT4）+ 旧版 Equation Editor OLE**，
  从 OLE 复合文档抽 MTEF v5/v3 字节流 → Python 解析 → MathML → OMML，**替换 docx XML**
- 验证语料：344 份中国物理试卷 / **7,888 个 MathType OLE**，**7,886/7,888** 成功
  （两个差异是 overbar 基字符保留问题）。覆盖分数、根、上下标、矩阵、堆叠、
  长除法、物理单位等。
- 依赖：`lxml` + `olefile` + `python-docx`，**外加 Office 自带 `MML2OMML.XSL`**（参数
  `--xsl` 指定，常见路径 `C:\Program Files\Microsoft Office\root\Office16\MML2OMML.XSL`）
- CLI：`mathtypejx convert input.docx -o output.docx`
  API：`convert_mathtype_to_omml("in.docx", "out.docx", parallel=True, max_workers=8)`
- GUI（Windows 拖放）：`pip install -e ".[gui]" && python -m mathtypejx_gui`

**对本项目讲义31 的落地**：用户那份 Word 转的 docx（134KB，105 个 OLE + WMF 预览）
先用 `mathtype2omml` 转一份**纯 OMML 的新 docx**，再走 LO docx→odt 中间层 + anydoc，
或直接 anydoc 读新 docx，**全部 105 个公式都能拿到 LaTeX**——彻底闭环。

限制：
- 只支持 `.docx`，**不支持二进制 `.doc`**
- Linux/WSL 需 `python3-tk` + DISPLAY
- 公式嵌入在 WMF 里时，需要 WMF 携带 MTEF 载荷（纯位图无法识别）

同类相关项目（备查）：
- `npofsi/docx-equation`（pypi 同名包）—— 反向：从 MathML 构建 docx 公式，
  支持 OMML 和 MathType 双输出路径，2026.6 发布
- `scalad/MathML2MathTypeEquation`（C#）—— 调用 MathType DLL 反向把 MathML 写回 Word
- 商业：GrindEQ（最完整，但收费）
- MathType 软件本身「剪切和复制预置」选 MathML/TeX 可单公式复制（手动，不批）

## 集成 mathtype2omml 进 docx-equations-to-md.ps1

脚本 `scripts/docx-equations-to-md.ps1` 已扩展为**三档回退**：

1. 已经是 OMML（`<m:oMath`）→ 直接 anydoc
2. 含 `Equation.DSMT4` 或 `Equation.3` 的 OLE → **`mathtypejx convert`**（要装
   `mathtypejx` 包并指定 `MML2OMML.XSL`，XSL 路径自动探 Office16/Office15

3. 上面两步都没成（极少）→ 走旧版 LibreOffice ODT 兜底

- `-MathtypeJx <exe>`：默认 `mathtypejx`（要求 PATH 可解析）
- `-Xsl <path>`：MML2OMML.XSL；不传自动探
- `-SkipMathtype2Omml`：跳过中间档，强制走 LO（调试用）

新增函数：
- `Test-MathTypeOle`：扫 word/document.xml 找 ProgID 字符串（不打开 oleObjectN.bin）
