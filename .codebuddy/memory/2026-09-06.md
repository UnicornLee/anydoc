# 2026-09-06

## 修正 earlier 错误假设：v3 字符映射其实没问题

之前记的"v3 `mtcode` 是 font-relative（font<<8|char），需要字体映射表"**是错的**。
实证（`replay_v3.py` 注释 + 实际解码）：v3 CHAR 的 `mtcode` 已是 **Unicode 码点**
（如 `0x0078` = 'x'），`char_latex` 的 `char::from_u32(mtcode)` 本就正确。汉字乱码是
**字节错位**的副产品，不是字符表问题。所以 anydoc 自带 MTEF 的 v3 修复重点是**记录布局**，
不是字符表。

## 本轮修复 mtef.rs 的两处 v3 真实 bug（基于 `mathtype2omml` 的 `records3.py` 权威表）

1. **模板 selector 重映射**：v3 与 v5 给同名模板编的 selector 号不同（v3 上标=15，
   v5 上标=28；v5 的 15 是 INTEG）。不重映射会把上标渲染成积分、分数渲染成箭头。
   新增 `v3_tmpl_selector(sel, variation) -> (v5_sel, v5_var)`，逐条照 `records3.py`
   的 `SELECTORS`/`VARIATIONS`/`SCRIPT_SELECTORS` 翻译（21-23 单/双/三重积分→INTEG
   variation 0/1/2 等）。

2. **embellishment 上/下标提取**：v3 的 `x²` 是 **CHAR 级 embellishment**——`x`(mtcode
   0x78) 后跟一个 tmSUP 模板，布局 `[size, base(空行), script(行)]`。原代码完全忽略
   `CHAR_EMBELL`，导致上标内容丢失。新增 `is_size` / `script_operand` / `subsup_operands`
   帮 SUP/SUB/SUBSUP 双臂从"非空的子 LINE"里取 script；embellishment 布局（首子是 SIZE）
   走这条，普通模板走 `[base, script]`。

   ⚠️ 曾试过"把 embellished CHAR 压栈、END 时弹栈"的做法，结果**截断公式**
   （obj1 丢掉 `=1`）。因为 v3 embellishment list 没有独立 END 终止符，会吞掉后续字符。
   已回退为**扁平模型**（embellishment tmSUP 作为 CHAR 的兄弟节点），只修正脚本提取，
   保证**不截断**。

## 二轮：剩余 3 个（obj85/87/88）已全解 → 105/105

**关键误判**：这 3 个不是 v3，是 **MathType v5**（version 字节=5，`"DSMT5"` 应用名）。
所以走的是 v5 路径，跟 v3 的 selector/embellishment 修复无关。两个真实 bug：

1. **EQN_PREFS styles 解析错**（主因）：anydoc 每个 style 无条件读 2 字节；参考实现
   （`mtef_ref/mtef.py readEqnPrefs`）是**读 1 字节，仅当非 0 再读 1 字节**（0 = "无样式"）。
   每个 0 样式多读 1 字节 → 在 EQN_PREFS 处错位，级联拖垮所有带 EQN_PREFS 的 v5 对象。
   修好后 obj88（868 字节，222 条记录）完整解到 EOF，得 `SΔAOB`（△AOB 面积，对应正文
   "三角形AOB面积"）。

2. **尾部杂字节**：obj85/87 的公式体已完整（CHAR + `END END`），但 `cb_size` 范围内末尾
   多 1 个游离字节（obj85=`0x38`，obj87=最后一个字节是裸 `RULER` tag 0x07）。原来一律
   `_ => return None` 把整个公式丢弃。改为：
   - 新增 `tag::RULER` 分支（跳过 options/nudge/nstops/stops，与 LINE 的 ruler 一致）；
   - 未知 tag 与 v5 options/FUTURE 长度字节**读到 EOF 时 `break`**（保留已收集内容），
     不再 `return None`。
   - 安全网：`decode_stream` 循环后本就有"输出为空则返回 None"的判断，所以垃圾流不会
     变成 `Some("")`。`_ => break` 只影响原本就失败的流，**不影响已通过的 102 个**。

结果：obj85=`x=0`、obj87=`b`、obj88=`SΔAOB`；`cargo test --lib` **287 全过**，
v5 语料（obj79/80/86）无回归。

**验证**：`$env:ANYDOC_MTEF_CORPUS='D:\tools\work\mtef_corpus'; cargo test --lib corpus_streams_decode`
现在 **105/105 全过**（断言不再故意 fail）。

## 三轮：复杂指数丢失根因 → 修复后与 LibreOffice 金标准对齐

转换整篇讲义时发现 6 个对象（obj1/26/48/60/63/88）丢指数/空分母，hexdump 手工解码 obj26
（`\frac{x^2}{1+x^2}`，61 字节）定位到**两个独立 bug**：

1. **`is_size()` 漏了 `SUB`(tag 11)**：v3 embellishment 上标的 size 占位符可能是 SUB
   （下标尺寸），原表只有 SIZE/FULL/SUB2/SYM/SUBSYM。漏掉 → tmSUP  embellishment 判断失败
   → 走"普通模板"分支 → 指数整个不渲染。补上 `t == tag::SUB`。
2. **`FRACT` 槽位取错**：v3 在分子/分母两个 slot LINE 之间夹一个**透明 FULL 标记节点**，
   原代码 `child_latex(idx,0/1)` 把分母取成那个空 FULL → 分母空白。新增
   `slot_lines()`（过滤出真正的 LINE 子节点），FRACT 取前两个 LINE。

修复后：obj1 `(x^{2}+x−1)^{x+3}=1`、obj26 `\frac{x^{2}}{1+x^{2}}`、obj48、obj60（含
`(\frac{DF}{AF})^{2}`）、obj63 `2x^{2}` 全部正确；**287 lib 全过、v5 语料无回归**。
之前记录的"复杂括号指数硬骨头"实际就是这两个 bug，并非不可解。

## Linux 生产环境的 LibreOffice 实验（重要结论）

- `load_input` 回退链现为：Windows 先 Word COM → LibreOffice（跨平台）
  → 原生 .doc 解析。`libreoffice_doc_to_docx` 用私有
  `-env:UserInstallation` profile 避免 soffice 单实例锁冲突。
- **实测 LibreOffice（本机 25.x）转这批 .doc 会完全丢 MathType OLE
  公式**：docx 里公式变成 `<a:blip></a:blip>` 空占位符，0 OMML、0 media，
  正文公式位置直接空缺。`MathTypeToMath` 注册表配置项试过无效。
- 结论：LibreOffice 只适合无 MathType 的普通 .doc；竞赛讲义语料的
  Linux 生产路径应是：离线预转 .docx（Windows+Word 一次性批处理），
  或把 anydoc 原生 MTEF 管线（src/shared/math/mtef.rs，进行中）做到
  与 Word COM 基准对齐（55 公式），彻底摆脱 office 套件。
